## Logic ที่อยู่ที่ controller/view (ไม่ใช่ service)

> จุดที่ business logic หลุดออกจาก Service มาอยู่ที่ controller/page — ต้องรู้ก่อนแก้ (verified จากโค้ดจริง)

- **Rate-limit ของ profile:** การเดารหัสผ่านปัจจุบันยังอยู่ใน `api/profile.php` เป็น closure session-based (5 ครั้ง/60s → 429) และนับเฉพาะ `credential_failure` · แต่การส่งลิงก์เปลี่ยนอีเมลใช้ `RateLimitRepository` + ตาราง `auth_rate_limits` ต่อผู้ใช้: 1 ครั้ง/60s และ 5 ครั้ง/ชั่วโมง
- ⚠️ **`includes/header.php` ถูก include กลางหน้า — ตัวแปรอยู่ scope เดียวกับเพจ** ห้ามใช้ชื่อที่เพจใช้ (`$shopId`, `$userId`, `$selectedMonth` …) ในนั้น เคยใช้ `$shopId` ในลูปเลือกร้านแล้วทับค่าของเพจด้วย "ร้านสุดท้ายในรายการ" · โค้ดของเพจที่อยู่ **หลัง** `require header.php` จะได้ค่าผิดทั้งหมด (มีเทสต์ `ShopContextGuardTest` ล็อกไว้)
- **ฟอร์มที่เขียนข้อมูลทุกอันต้องมี `shop_context_field($shopId)` คู่กับ `csrf_field()`** — 7 ฟอร์มใน `add-record.php` (3), `history.php` (2), `dashboard.php` (2) · controller ตรวจด้วย `ensure_shop_context_or_respond()` ตอบ 409 เมื่อ session ชี้คนละร้านกับตอนที่หน้าถูกเรนเดอร์ ⚠️ guard ต้องวาง **หลัง** `$shopId` ถูกกำหนดค่า · ฟอร์มที่ไม่ส่งค่านี้มาจะผ่านโดยตั้งใจ (กันอุบัติเหตุ ไม่ได้กันการโจมตี — สิทธิ์ยังตรวจที่ Service)
- **ฟอร์มหลักในหน้าบันทึกเติมค่าเดิมของวันนั้นเสมอ** (`RecordService::getRecordForDate()` ฝั่งเซิร์ฟเวอร์ + JS ดึงผ่าน `api/month-grid.php` ตอนเปลี่ยนวัน) — การบันทึกเป็น upsert ที่เขียนทับทุกช่อง ถ้าไม่เติมโน้ตเดิมกลับมา การแก้แค่ยอดขายจะลบโน้ตทิ้ง
- ⭐ **`normalize_money_string()` ใน `includes/functions.php` คือจุดเดียวของกฎการอ่านตัวเลขเงิน** — ฟอร์มเดี่ยว · ตารางหลายวัน · เป้าหมาย · ไฟล์ CSV ต้องผ่านตัวนี้ทั้งหมด (`parse_decimal_input()` เรียกต่อ) · **คู่แฝดฝั่ง JS** = `cleanAmountCell()` ใน `add-record.php` ต้องให้ผลเหมือนกันทุกค่า
  · รับ: `1234` `1234.56` `1234,56` `1,234.56` `1.234,56` `1,234,567.89` `1 234,56` `฿1,234.56`
  · **ปฏิเสธ (ห้ามเดา):** `1.234` / `1,234` (อ่านได้ทั้งหลักพันและทศนิยม 3 ตำแหน่ง) · `1.2.3` · `1..2` · `1e3` · ทศนิยมเกิน 2 ตำแหน่ง — หลักเดียวกับ "วันที่กำกวม"
  · ⚠️ ประวัติ: เคยลบจุลภาคทิ้งเสมอ (`1234,56` → 100 เท่า) แล้วเปลี่ยนเป็นเดาตัวคั่น (`1.234` → 1000 เท่า) **ห้ามกลับไปเดาอีก**
- **`monthly_goals`: ช่องที่ไม่ได้กรอกมา = คงค่าเดิม ไม่ใช่ล้างทิ้ง** (`GoalService::upsertGoal` อ่านของเดิมใต้ล็อกก่อนเขียน) — ฟอร์มที่เปิดค้างไว้เคยล้างเป้าที่อีกแท็บเพิ่งตั้ง · จะล้างทั้งเดือนใช้ปุ่ม "ลบเป้าหมาย"
- **โน้ต: "ช่องว่าง" ต่างจาก "ไม่มีคอลัมน์"** — ตัวกันของ `rejectBlankCellsOverwritingExistingDays()` ใช้ธง `note_was_missing` (ไฟล์ CSV ที่ไม่มีคอลัมน์โน้ตเลย) ไม่ใช่ "ค่าที่ส่งมาว่าง" · ตารางกรอกหลายวันเติมโน้ตเดิมให้เห็นก่อน (JS `change` ของ `record_date[]`) การล้างจึงเป็นการตั้งใจ ⚠️ **แก้แล้ว: วันอนาคตที่มีข้อมูลอยู่แล้วเติมให้ได้** — `buildEditableMonthGrid()` ส่ง `future_days_with_records` แยกคีย์มาให้ฟอร์มวันเดียวใช้ (ตารางกรอกหลายวันยังอ่านจาก `days` ซึ่งตัดที่วันนี้เหมือนเดิม) · **เดิมเตือนอย่างเดียวแล้วปล่อยให้โน้ตหาย** ทั้งที่ข้อมูลมีให้ใช้อยู่แล้ว — "เตือนผู้ใช้" ไม่ใช่การแก้บั๊ก
- ⚠️⚠️ **ตารางกรอกหลายวันเคยลบโน้ตเดิมทิ้งเงียบ ๆ พร้อมตอบว่าสำเร็จ** — ทั้งที่ไฟล์ CSV ที่ทำสิ่งเดียวกันเป๊ะ ๆ ถูกปฏิเสธ
  · ตารางเติมโน้ตเดิมกลับมาให้เห็นก่อน ช่องว่างจึงแปลว่า "ตั้งใจล้าง" — **แต่จริงเฉพาะเมื่อการเติมนั้นเกิดขึ้นจริง**
  · ⚠️ ตัวเติมเคยไม่ทำงานใน 2 ท่าที่ใช้จริงบ่อยที่สุด: (1) พิมพ์ยอดก่อนแล้วค่อยเลือกวันที่ — เงื่อนไข "มีช่องไหนกรอกแล้วให้ออกทันที" ข้ามช่องโน้ตที่ผู้ใช้ไม่ได้แตะไปด้วย · (2) วางจาก Excel — `input.value = …` **ไม่ทำให้ event `change` ทำงาน** ตัวเติมจึงไม่เคยถูกเรียกเลย (ตอนนี้ยิง event เองหลังวาง ทั้งสองทางเดินโค้ดชุดเดียวกัน)
  · ⚠️⚠️ **`populateFromDays()` ต้องตั้งธง `note_checked` ให้แถวที่มันเติมด้วย** — ตัวเติม
    คือสิ่งเดียวที่ทำให้ผู้ใช้ "เห็นโน้ตเดิม" ถ้าเติมแล้วไม่ปักธง เซิร์ฟเวอร์จะไม่รู้ว่าแถวนั้น
    ถูกตรวจแล้ว → ตัวกันฝั่งเซิร์ฟเวอร์ปฏิเสธทั้งชุดทั้งที่ผู้ใช้ทำถูกทุกอย่าง
  · ⚠️ **ฝั่งเซิร์ฟเวอร์ต้องมีตัวกันด้วย** — ธง `note_checked[]` ต่อแถว: โหลดข้อมูลเดือนไม่สำเร็จแล้วจะทับโน้ตที่มีอยู่ = ปฏิเสธทั้งชุดด้วยข้อความเดียวกับ CSV · เห็นโน้ตเดิมแล้วลบเอง = ล้างได้ตามปกติ (ไม่งั้นลบโน้ตผ่านตารางไม่ได้เลยตลอดกาล)
- ✅ **[เจ้าของระบบตัดสิน 2026-08-10 — ยอมรับข้อจำกัดนี้ ไม่ต้องแก้] สองแท็บแก้วันเดียวกัน = ใครบันทึกทีหลังชนะทั้งแถว**
  · ธง `note_checked` ถูกตั้งตอนที่หน้าเว็บ **เห็นข้อมูลของวันนั้นแล้ว** ซึ่งเป็นภาพ ณ เวลาที่โหลด
    ถ้าอีกแท็บเพิ่งเพิ่มโน้ตหลังจากนั้น แล้วแท็บแรกกดบันทึกโดยเว้นช่องโน้ตไว้
    → โน้ตใหม่ถูกล้าง โดยตัวกัน "เว้นช่องแล้วของเดิมหาย" ไม่ทักอะไร (มันเชื่อธง)
  · ยืนยันด้วยข้อความ: **"ยอมรับได้"** — การบันทึกของระบบนี้เป็นการเขียนทับทั้งแถวโดยธรรมชาติ
    (upsert ทุกช่อง) พฤติกรรม "ใครบันทึกทีหลังชนะ" จึงสอดคล้องกับที่เหลือ และระบบมีผู้ใช้ 2 คน
  · ⚠️ **ห้ามเพิ่มกลไกกันเรื่องนี้โดยไม่ถามเจ้าของระบบก่อน** — ทางแก้ทุกทาง (ตรวจซ้ำก่อนเขียน ·
    เก็บเวอร์ชันของแถว · ล็อกแถวข้ามคำขอ) ทำให้การบันทึกช้าลงหรือปฏิเสธผู้ใช้บ่อยขึ้น
    ซึ่งแลกไม่คุ้มกับความถี่ที่เกิดจริง
  · ⚠️ **ถ้าวันหนึ่งมีคนใช้พร้อมกันหลายคนบนร้านเดียวกัน ต้องกลับมาทบทวนข้อนี้**
- **ตัวกัน "เว้นช่องแล้วของเดิมหาย" ใช้กับทุกทางที่เขียนข้อมูล** (`rejectBlankCellsOverwritingExistingDays()`) — ทั้ง CSV และตารางกรอกหลายวัน · คุมทั้ง รายได้/ค่าแอด/**โน้ต** ⚠️ เตือนเฉพาะเมื่อ "มีของจริงจะหาย" (ค่าเดิม `0` หรือโน้ตว่าง ไม่นับ) และรายงาน **แถวที่ผู้ใช้เห็นเป็นแถวแรก** ไม่ใช่วันที่น้อยสุด
- **หน้าตั้งรหัสผ่านใหม่ต้องพา token กลับมาเมื่อบันทึกไม่ผ่าน** (`api/auth.php` → `/reset-password.php?token=…`) — ไม่งั้นพิมพ์รหัสยืนยันผิดครั้งเดียวจะถูกเด้งไปหน้า "ลืมรหัสผ่าน" พร้อมข้อความที่ไม่จริง และ `reset-password.php` ต้องไม่เขียนทับ flash error ที่ API ตั้งไว้
- ✅ **[เจ้าของระบบตัดสิน 2026-08-07] ช่องยอดที่เว้นว่างในไฟล์ CSV = ปฏิเสธ ไม่ใช่ 0**
  · เดิม CSV แปลงช่องว่างเป็น 0 ให้เอง โดยคอมเมนต์อ้างว่า "UI ก็ปล่อยว่างได้" ซึ่ง **ไม่จริง** — ทางเขียนอีกสองทางบังคับกรอกทั้งคู่ (ฟอร์มวันเดียว `required`+`parse_decimal_input` · ตารางกรอกหลายวัน `upsertManyRecords`) · CSV เป็นทางเดียวที่เดาแทนผู้ใช้
  · เหตุผลที่เปลี่ยน: **ความเสียหายสองฝั่งไม่เท่ากัน** — เดาเป็น 0 แล้วผิด ได้ "วันที่รายได้ ฿0 แต่จ่ายค่าแอดจริง" คือวันขาดทุนปลอมที่ไหลเข้าทุกรายงาน (กำไรเฉลี่ยต่อวัน · วันแย่สุด · ROAS · เป้า · กราฟ) โดยผู้ใช้ไม่รู้ตัว · ปฏิเสธแล้วผิด แค่พิมพ์ 0 เอง
  · ไฟล์ที่ระบบ export ออกไปไม่เคยมีช่องยอดว่าง ท่า "โหลดออกไปแก้ใน Excel แล้วนำเข้ากลับ" จึงไม่กระทบ
  · ⚠️ **ผลข้างเคียง: กิ่ง "ช่องว่างทับยอดจริง" ของ `rejectBlankCellsOverwritingExistingDays()` ไม่มีทางถูกกระตุ้นผ่าน CSV อีกแล้ว** (ตารางกรอกหลายวันไม่เคยตั้งธง `revenue_was_blank` อยู่แล้ว) · เก็บไว้เป็นด่านที่สองเผื่อมีคนคลายกติกากลับ · `RecordServiceOverwriteGuardTest` เรียก `upsertManyRecords()` ตรง ๆ พร้อมตั้งธงเอง และเขียนกำกับไว้ว่าเป็นการยืนยัน **สัญญาของเมธอด** ไม่ใช่เส้นทางที่ผู้ใช้เดินได้จริง
  · ⚠️ กิ่ง **โน้ต** ยังทำงานปกติ (ไฟล์ที่ไม่มีคอลัมน์โน้ตเลย + ธง `note_checked[]` ของตาราง) — ห้ามลบตัวกันนี้ทิ้ง
- **สูตร profit/ROAS ซ้ำใน view:** `RecordService->getRecentRecords()` คืน row ดิบ → `add-record.php` (ตาราง "รายการล่าสุด") คำนวณ profit/ROAS เองในเพจ ⚠️ **แก้สูตร profit/ROAS ต้องตามไปอัปเดต view นี้ด้วย ไม่ใช่แค่ service**
- **`$today` seam:** service ที่ผลลัพธ์ขึ้นกับวันที่ (`RecordService`, `AnnualService`, `OverviewAnnualService`, `ExportService`, `DashboardService`) รับ `?string $today = null` ท้าย param ไว้ให้เทสต์ล็อกวันได้ — **ถ้าเพิ่ม logic ที่อ่านวันที่ ต้องรับ seam ต่อไปด้วย** ไม่งั้นบางส่วนอ้างวันนี้จริงขณะที่ส่วนอื่นใช้ค่าที่ส่งเข้ามา (เคยเป็นบั๊กใน `DashboardService::resolveRange`) · ใน `RecordService` ใช้ `resolveToday()` ตัวเดียว (เคยคัดลอกบล็อกเดิมไว้ 4 ที่)
- ✅ **[เจ้าของระบบตัดสิน 2026-08-06] `daily_records` เป็น actuals เท่านั้น — ห้ามบันทึกวันอนาคต**
  · ยืนยันด้วยข้อความ: "บันทึกข้อมูลวันอนาคตไม่ได้แล้ว ไม่ต้องบันทึกล่วงหน้าก็ได้"
  · **อย่าย้อนกลับเป็น "ลงล่วงหน้าได้"** — คอมเมนต์เก่าในโค้ดที่เขียนว่า "ลงวันที่ล่วงหน้าทำได้ (บางคนตั้งใจ)" ไม่ใช่กติกาปัจจุบันแล้ว
  · ⚠️ **แต่โค้ดที่รองรับ legacy future rows ต้องคงไว้** — ข้อมูลที่ลงไว้ก่อนกติกานี้ยังอยู่ในฐานข้อมูลได้ ถ้าถอดออก แถวพวกนั้นจะแก้/ลบผ่านหน้าเว็บไม่ได้อีกเลย ได้แก่:
    - `buildEditableMonthGrid()` → `future_days_with_records` (ฟอร์มวันเดียวเติมค่าเดิมได้)
    - `history.php` เปิดเดือนอนาคตได้เมื่อเดือนนั้นมีข้อมูลจริง (ไม่งั้นลบแถวเก่าไม่ได้)
    - รายงาน/analytics ปีปัจจุบันตัดที่วันนี้ (ไม่ให้แถวเก่าโผล่ในยอดรวม)

- **ตัวกัน "ช่องว่างทับของเดิม" ต้องอ่านข้างใน transaction หลังจองแถวร้านแล้ว** — `rejectBlankCellsOverwritingExistingDays()` อยู่หลัง `beginTransaction` + `lockForWrite` · เดิมอ่านก่อนเปิด transaction อีกแท็บที่บันทึกแทรกเข้ามาระหว่างนั้นจะถูกทับด้วยศูนย์พร้อมข้อความ "สำเร็จ" ⚠️ **ห้ามใส่ `SELECT` ธรรมดาไว้ระหว่าง `beginTransaction` กับตัวกันนี้** — REPEATABLE READ จะตรึงภาพไว้ตั้งแต่ query แรก ตัวกันจะกลับไปอ่านของเก่าอีกโดยไม่มีอะไรเตือน (`lockForWrite` เป็น locking read จึงไม่ตรึงภาพ)
- **คอลัมน์ "เทียบครั้งก่อน" ใน CSV ห้ามขึ้นต้นด้วย `+`** — Excel แปลงเซลล์ที่ขึ้นต้นด้วย `+` เป็น *สูตร* (มรดก Lotus 1-2-3) ช่องนี้จึงเป็นสูตรช่องเดียวในไฟล์และพังบนเครื่องที่ตั้งทศนิยมเป็นจุลภาค · เครื่องหมายลบไม่มีปัญหา (Excel อ่าน `-50.0%` เป็นจำนวนลบ) · `ExportServiceTest::testNoSystemGeneratedCellStartsAFormula` กวาดทุกเซลล์ที่ไม่ใช่โน้ต
- ⚠️ **แปลง error → รหัสสถานะ ต้องผ่าน `infer_http_status_from_error()` ที่เดียว** — เดิมมี inline `str_contains($err,'ไม่มีสิทธิ์') ? 403 : 422` อีก 7 จุดใน 5 ไฟล์ (`export.php` กับ `export-xlsx.php` ทำงานคู่กันแต่ใช้คนละวิธี) · **ตอนที่เจอทั้งสองให้ผลเท่ากันจริง** เพราะ service ที่ endpoint กลุ่มนั้นเรียกคืนเฉพาะข้อความที่มี "ไม่มีสิทธิ์" — ปัญหาคือกับดักอนาคต: วันที่ service คืน `Unauthorized` (มีแล้วใน `ProfileService`) หรือข้อความ CSRF/method กลุ่ม inline จะตอบ 422 เงียบ ๆ ผิดความหมาย · `SharedHelperContractTest::testNobodyMapsErrorsToStatusCodesByHand()` กวาดไว้แล้ว
- ⚠️ **Service ห้ามเขียน SQL เอง — `SharedHelperContractTest::testServicesDoNotWriteSqlThemselves()` กวาดไว้** · ⚠️⚠️ **`AuthService` ถูกยกเว้นไว้ชั่วคราว** (เขียน SQL ของ `auth_rate_limits` เอง 8 จุด ทั้งที่ `RateLimitRepository` ทำเรื่องเดียวกันและถูกใช้โดย `ProfileService` อยู่แล้ว) — ย้ายไม่ใช่งานกลไก เพราะมี fallback ไปนับใน session เมื่อตารางไม่พร้อม ซึ่งเป็น **นโยบาย** ไม่ใช่การเข้าถึงข้อมูล ต้องตัดสินก่อนว่าวางชั้นนั้นไว้ตรงไหน · **ห้ามเพิ่มชื่อไฟล์เข้ารายการยกเว้น**
- **405 ต้องมาคู่กับ header `Allow: POST` เสมอ** (`ensure_post_request_or_respond`) — RFC 9110 บังคับ ไม่งั้นฝั่งที่เรียกได้แต่ "ห้ามใช้วิธีนี้" โดยไม่รู้ว่าต้องใช้อะไรแทน
- **`config_positive_int()` ห่อด้วย `function_exists`** — `includes/config.php` ถูก include ได้จากหลายทาง เดิม include ซ้ำ = fatal "Cannot redeclare" ทั้งที่ค่าคงที่ข้างล่างกันตัวเองด้วย `if (!defined(...))` อยู่แล้ว ⚠️ และอ่าน env ด้วย `getenv() === false` ไม่ใช่ `?: ''` เพราะ `"0"` เป็น falsy — ค่าที่ตั้งผิดเป็น 0 เคยเงียบสนิทเหมือนไม่ได้ตั้ง
- **JS ที่คัดลอกกติกามาจาก PHP ต้องมีเทสต์เทียบเสมอ** — `BrowserScriptParityTest` **ดึงตัวฟังก์ชันออกมาจาก `add-record.php` ตรง ๆ** (หา `const <ชื่อ> = ` แล้วนับวงเล็บจนถึง `;` นอกวงเล็บ) ไปรันด้วย node แล้วเทียบผลกับ PHP ชุดค่าเดียวกับ `MoneyInputParsingTest` ⚠️ **ห้ามคัดลอกโค้ด JS มาไว้ในเทสต์** ไม่งั้นได้สำเนาที่ 3 ให้เพี้ยนอีก · เปลี่ยนวิธีประกาศฟังก์ชัน (เช่นไปเป็น `function foo()`) เทสต์จะแดง — ต้องมาอัปเดตตัวดึง ไม่ใช่ปิดเทสต์ · ไม่มี node = skip (CI ของ GitHub มี node ติดมาอยู่แล้ว)
- ⚠️ **การ์ด "เทียบวันเดียวกันในสัปดาห์" ต้องจบช่วงที่วันนี้ ไม่ใช่สิ้นเดือน** — ตาราง "กำไรเฉลี่ยตามวัน" ที่อยู่ใต้มันในหน้าเดียวกันใช้ `resolveWeekdayWindow()` ซึ่งจบที่วันนี้ · เดิมการ์ดไล่ `Y-m-t` สองบรรทัดบนจอเดียวกันจึงใช้คำว่า "เดือนนี้" เหมือนกันแต่คนละฐาน (วัดจริง: การ์ดบอกเฉลี่ยจันทร์ ฿9,000 + ป้าย "ต่ำกว่าปกติ" ขณะที่ตารางบอก ฿1,000 จาก 1 วัน — จันทร์ 3 วันนั้นยังมาไม่ถึง)
  · ⚠️ **เทสต์ของการ์ดนี้ต้องปัก `$today` เสมอ** — เดิม 3 ตัวไม่ปัก ผลจึงเปลี่ยนตามวันที่รันจริง (เทสต์ข้าง ๆ ในไฟล์เดียวกันมีคอมเมนต์เตือนไว้แล้วแต่ตัวอื่นไม่ได้ทำตาม)
- **เกณฑ์ตัวอย่างขั้นต่ำของวันในสัปดาห์ = `RecordService::WEEKDAY_MIN_SAMPLE`** — `comparable` (มีอะไรให้เทียบไหม) ยังเป็น `>= 1` แต่การฟันธง "สูงกว่า/ต่ำกว่าปกติ" ใช้ `trend_reliable` (`>= 3`) เกณฑ์เดียวกับที่ตารางแยกตามวันใช้เลือกวันดี/วันเงียบ · **อย่าฮาร์ดโค้ด 3 ซ้ำในเพจ**
