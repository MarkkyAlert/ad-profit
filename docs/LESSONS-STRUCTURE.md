## โครงสร้างที่ต้องรู้ (gotchas)

- **Response layer:** controller ตอบผ่าน `api_respond()` — เลือก JSON (`jsonResponse`, กรณี XHR/`wants_json`) หรือ redirect+flash (กรณี form) อัตโนมัติ + `infer_http_status_from_error()`. Service คืน result-array, controller เป็นคนแปลงเป็น response
- **Frontend เป็น server-render เป็นหลัก:** state-changing = native `<form method="post" action="/api/...">` + `csrf_field()` + hidden `action` → redirect+flash; ปุ่มยืนยัน/loading/กันกดซ้ำ อยู่ใน `includes/footer.php`; **CSRF ไม่ได้ expose เป็น meta/JS**
- ⚠️ **AJAX มีจุดเดียวที่ตั้งใจ (controlled exception):** `GET api/month-grid.php` — โหลดข้อมูลทั้งเดือนมาเติมตาราง bulk ในหน้า `add-record.php` **read-only ไม่เปลี่ยน state จึงไม่มี CSRF** (auth ผ่าน session เหมือน `*-data.php`) · **การเขียนทุกอย่างยังเป็น form POST + CSRF เหมือนเดิม** · **ห้ามเพิ่มจุด AJAX ใหม่เพราะ "add-record ก็ทำ"** — ถ้าจะเพิ่มต้องเป็นการตัดสินใจที่มีเหตุผลชัดเจนเฉพาะกรณีนั้น
- **`api/dashboard-data.php`, `overview-data.php`, `annual-data.php` ไม่ถูกเรียกจาก UI** (data page เรียก Service ตรงในเพจ) — อย่าเข้าใจผิดว่าหน้าเว็บ fetch endpoint พวกนี้
- ✅ **กลไก transaction/กันซ้ำ มีเทสต์คุมครบแล้ว** (8 ส.ค. 2569 — จาก transaction safety review)
  · **register rollback** (`users` + `shops` ใน tx เดียว) → `AuthServiceRegisterTest::testAFailedShopCreationLeavesNoOrphanUser()` ใช้ `FailingShopRepository` (คลาสลูกจริง ไม่ใช่ mock — ให้ทุกอย่างอื่นเดินบน DB จริง) · ⚠️ ถ้า rollback หาย จะเหลือผู้ใช้ที่ไม่มีร้าน **แล้วสมัครใหม่ด้วยอีเมลเดิมไม่ได้อีก** เพราะ `uq_users_email` = บัญชีตายถาวร
  · **กดบันทึกซ้ำ/refresh หลัง POST ระดับ endpoint** → `RecordActionEndpointTest::testSubmittingTheSameDayTwiceUpdatesInsteadOfDuplicating()` · เดิมมีแค่ระดับ service ทางที่ผู้ใช้เดินจริงไม่เคยมีเทสต์ยิง upsert ซ้ำเลย
  · ⚠️⚠️ **power-proof ของ UNIQUE key ต้องแก้ที่ `database/schema.sql` ไม่ใช่ `ALTER TABLE` บน test DB** — `IntegrationTestCase::loadSchema()` โหลดสคีมาใหม่ทุกครั้ง การถอด index จาก DB ตรง ๆ จะถูกคืนก่อนเทสต์เห็น (อาการ: `ALTER … ADD` ตอบ `Duplicate key name` แล้วเทสต์เขียวทั้งที่ควรแดง)
- **กันกดซ้ำพึ่ง unique key ระดับ DB + row lock เท่านั้น** — ตาราง `idempotency_requests` + repository + cron ถูกลบทิ้งแล้ว (ไม่เคยถูกเรียกจากที่ไหนเลย) ⚠️ ผลข้างเคียงที่ดี: schema ไม่ต้องใช้คอลัมน์ชนิด JSON อีกต่อไป → host ไม่ต้องรองรับ JSON · **การลบซ้ำ (กด back แล้ว submit ใหม่) ตอบว่าสำเร็จแล้ว** — `deleteRecord`/`deleteGoal` ทำ idempotent เอง: หาไม่เจอในร้านปัจจุบัน → เช็กก่อนว่าอยู่ในร้านอื่นของผู้ใช้ไหม (ถ้าใช่ = ตอบ error ให้สลับร้าน) ถ้าไม่มีที่ไหนเลย = ผลตรงกับที่ขอ → ตอบสำเร็จ ⚠️ **ห้ามเพิ่ม flag/ข้อความแยกให้เคสนี้** ต้องเหมือนการลบที่สำเร็จจริงทุกไบต์ ไม่งั้นบอกใบ้ว่ารายการของคนอื่นมีอยู่จริงไหม · `ShopService::deleteShop` **ตั้งใจไม่ทำ idempotent** (เหตุผลอยู่ในคอมเมนต์ของเมธอด)
- ⚠️⚠️ **ตารางใหม่ต้องมาลงทะเบียนกับ Schema Guard ครบทั้ง 5 รายการ — และตอนนี้มีตัวกวาดบังคับแล้ว**
  · `email_change_requests` เคยตกสำรวจทั้ง 5 รายการ ทั้งที่สร้างตามแบบ `password_reset_tokens` ทุกอย่าง (unique key คู่เดียวกัน · FK cascade เหมือนกัน · แม้แต่คอมเมนต์ "ขอใหม่ทับของเดิม" ก็เหมือนกัน)
  · **วัดจริง 2 กรณี:** (1) ฐานข้อมูลขาดตารางนี้ตารางเดียว → guard ตอบว่า "ผ่าน" แอปเปิดได้ปกติทุกหน้า จนกว่าจะมีคนกดเปลี่ยนอีเมลถึงจะเจอทางตัน — ซึ่งคือกรณี "อัปโหลดโค้ดใหม่แล้วลืมรัน migration" และอาจไม่มีใครรู้ไปหลายเดือน · (2) migration ที่ทำมือแล้วพิมพ์ `KEY` แทน `UNIQUE KEY` → ขอเปลี่ยนอีเมล 2 ครั้งแล้ว **ลิงก์ทั้งสองใบยังใช้ได้** ทั้งที่กติกาคือขอใหม่ต้องทำให้ของเก่าใช้ไม่ได้ทันที (กุญแจตัวนั้นคือสิ่งเดียวที่บังคับกติกานี้)
  · ⚠️ **ตัวกวาดเดิมเทียบกับรายชื่อที่พิมพ์ไว้ตายตัว จึงไม่มีวันทักตารางใหม่** — ตอนนี้ `SchemaGuardTest` กวาดจาก `information_schema` ของฐานข้อมูลจริงแทน (unique index · ตาราง/InnoDB · FK cascade) เพิ่มตารางแล้วลืมลงทะเบียน = แดงทันที · **พอเปลี่ยนวิธีกวาด มันเจอช่องที่สองเองทันที: `auth_rate_limits` ก็ไม่เคยถูกตรวจว่าเป็น InnoDB**
- **Schema Guard ใน `includes/bootstrap.php`:** ถ้า schema ไม่ตรง (ตาราง/คอลัมน์/index ที่กำหนด) ระบบตอบ 503 / CLI exit(1) ควบคุมด้วย flag `SCHEMA_GUARD_ENABLED` — **เวลาแก้ schema ต้องอัปเดต guard ด้วย**
- ⚠️ **การเปลี่ยน collation ไม่ได้ "แยกอย่างเดียว" — มันรวมด้วย** มี 89 คู่อักขระที่ `utf8mb4_unicode_ci` ถือว่าต่างแต่ `utf8mb4_unicode_520_ci` ถือว่าเหมือน (กลุ่มเวียดนาม `D`/`Đ`/`Ð`/`đ` และ `6`/`ↅ`) · migration จึงต้อง **เติมเลขต่อท้ายชื่อที่จะชนกันก่อน** แล้วค่อย ALTER ไม่งั้นล้มด้วย duplicate key พร้อม error ที่ไม่พูดถึงชื่อร้านซ้ำเลย และการแก้ไปไม่ถึงเครื่องจริง
- ⚠️ **Schema Guard ต้องตรวจ `COLLATION_NAME` ด้วย** — `COLUMN_TYPE` มองไม่เห็น collation · ถ้า migration ล้มกลางคัน แอปจะบูตขึ้นมารายงานว่าปกติ ทั้งที่บั๊กอิโมจิยังอยู่ครบ
- ⚠️ **ตัวจำกัดการเดารหัสผ่านต้อง "นับก่อน แล้วดูเลข" ไม่ใช่ "ถามว่าเกินยัง แล้วค่อยนับ"** — เดิมมี `password_verify()` (~100ms) คั่นระหว่างอ่านกับเขียน คำขอที่ยิงพร้อมกันจึงอ่านค่าเดิมกันหมด · **วัดจริง: เพดาน 5 แต่ยิงพร้อมกัน 40 ผ่านเข้าไป 28** (ทีละครั้งผ่าน 5 ตามที่ควร) · `AuthService::reserveAttempt()` จองแบบ atomic แล้วคืนเลขที่นับได้ → เหลือ 2
- ⚠️ **ตั้ง `display_errors` ก่อนแตะระบบไฟล์ใน `bootstrap.php`** — ถ้า `LOG_FILE` ชี้ไปที่เขียนไม่ได้ `mkdir()` จะเตือนก่อนที่แอปจะปิดการแสดง error ผลคือ **เส้นทางเต็มของเซิร์ฟเวอร์หลุดออกไปในหน้าเว็บ** และ response ถูกส่งไปแล้ว → `header()` ทุกตัวหลังจากนั้นไม่ทำงาน หน้าที่ควรตอบ 503 กลายเป็น 200 · เขียน log ไม่ได้ต้องไม่ทำให้หน้าเว็บพัง แต่ก็ต้องไม่เงียบ (แจ้งผ่านปลายทางปริยายของ host แทน)
- ⚠️ **`phpunit.xml` ตั้ง `failOnRisky="true"`** — ไม่งั้นเทสต์ที่ไม่ยืนยันอะไรเลย (เช่นลูปที่รายชื่อว่าง) จะขึ้นแค่ "risky" แล้ว exit code ยัง 0 · CI เขียวทั้งที่ตัวกันหายไปแล้ว
- ⚠️ **collation ของ `shops.name` คือกติกา "ชื่อร้านซ้ำกันไหม"** — `uq_shops_user_name` ใช้มัน และ `findByNameAndUserId()` เทียบด้วย `name = :name` เฉย ๆ · ต้องเป็น **`utf8mb4_unicode_520_ci`** เท่านั้น
  · `utf8mb4_unicode_ci` (UCA 4.0.0) **ไม่ให้น้ำหนักกับอักขระนอกระนาบพื้นฐาน** → อิโมจิทุกตัวเท่ากันหมด · ผู้ใช้ที่มีร้าน 🚀 แล้วสร้างร้าน 🎉 ถูกพาไปร้าน 🚀 พร้อมข้อความว่าสำเร็จ แล้วข้อมูลลงผิดร้านทั้งหมด (เกิดขึ้นได้จริง พิสูจน์แล้ว)
  · `utf8mb4_bin` แก้อิโมจิได้แต่ทำให้ "ร้าน A" ≠ "ร้าน a" ซึ่งเปลี่ยนพฤติกรรม "พิมพ์ชื่อเดิม = สลับไปร้านนั้น" · 520_ci แก้อิโมจิโดยไม่กระทบส่วนนั้น
  · **ข้อความตอนสลับร้านต้องบอกชื่อร้านปลายทางเสมอ** — ระบบถือว่า "ร้าน A" = "ร้าน a" = "Café" = "Cafe" ผู้ใช้จึงถูกพาไปอีกร้านได้โดยไม่รู้ตัว
- ⚠️ **Schema Guard ต้องตรวจ "ชนิด" ไม่ใช่แค่ "ชื่อ"** — เดิมดูแค่มีตาราง/คอลัมน์/index ชื่อนี้ไหม · ย่อ `note` เหลือ VARCHAR(50) · เปลี่ยน `revenue` เป็น DECIMAL(8,2) · ลบ foreign key · เปลี่ยนเป็น MyISAM — **ผ่านหมดทุกอย่าง** ทั้งที่แต่ละอย่างทำข้อมูลหายคนละแบบ (FK หาย = ลบร้านแล้วข้อมูลค้าง · MyISAM = `rollBack()` ไม่ทำอะไรเลย) · ตอนนี้ตรวจ `COLUMN_TYPE` + `ENGINE` + `DELETE_RULE` ด้วย (`schema_required_column_types()`, `schema_transactional_tables()`, `schema_required_cascades()`)
- ⚠️ **ความยาวในโค้ดกับความยาวคอลัมน์ต้องเป็นค่าคงที่ที่ผูกกันไว้** — `RecordService::NOTE_MAX_LENGTH` · `ShopService::MAX_SHOP_NAME_LENGTH` · `ProfileService::MAX_DISPLAY_NAME_LENGTH` · `MAX_AMOUNT`/`AMOUNT_DECIMALS` ↔ `DECIMAL(12,2)` · `SchemaContractTest` ล็อกทุกคู่ · เดิมเป็นเลขลอย ๆ ตัวกันฝั่ง PHP จึงทำงานถูกเพราะ "บังเอิญ" ตรงกับคอลัมน์
- ⚠️ **ห้ามใช้ `PDO::MYSQL_ATTR_INIT_COMMAND`** — ถูกประกาศเลิกใช้ใน PHP 8.5 แล้ว **คำเตือนหลุดลงกลางหน้าเว็บ** ที่ผู้ใช้เห็น (เจอมาแล้ว เทสต์ `PageRenderTest` จับได้) · ตัวแทนใหม่ `Pdo\Mysql::ATTR_INIT_COMMAND` มีเฉพาะ 8.4+ ซึ่งสูงกว่าที่โปรเจกต์รองรับ (8.3) → **สั่ง `SET SESSION sql_mode` เป็น query ธรรมดาหลังต่อ** ทำงานเหมือนกันทุกเวอร์ชัน
- ⚠️ **`includes/database.php` ตั้ง `sql_mode` เองหลังต่อฐานข้อมูล** — ห้ามพึ่งค่าปริยายของโฮสต์ · ถ้าไม่ strict MySQL จะ "ตัดให้พอดี" แทนที่จะปฏิเสธ (โน้ต 256 → 255 · ยอด 10,000,000,000 → 9,999,999,999.99) เงียบสนิทและรายงานว่าสำเร็จ ⚠️ **ทศนิยมเกิน 2 ตำแหน่งถูกปัดเงียบในทุก sql_mode** — `hasTooManyDecimals()` เป็นด่านเดียวถาวร
- **`database/schema.sql` เป็น DROP + CREATE** — ห้ามรันทับ database จริง; ถ้าจะแก้โครงบน DB ที่มีข้อมูล ใช้ `ALTER` แยกต่างหาก ⚠️ ไฟล์**ขึ้นต้นด้วย `CREATE DATABASE ad_profit; USE ad_profit;` (hardcode ชื่อ DB จริง)** → `mysql < schema.sql` บนเซิร์ฟเวอร์ = **DROP ตารางใน `ad_profit` จริงทันที**; integration test loader (`tests/Integration/IntegrationTestCase.php`) จึง**ตัด 2 บรรทัดนี้ทิ้ง** ให้ DDL ลงเฉพาะ DB ที่ต่ออยู่
- ⚠️ **`session_start()` ต้องตั้ง `gc_maxlifetime` ให้ยาวกว่า idle timeout ของแอป** — ค่าปริยายของ PHP คือ 1440 วิ (24 นาที) ตัวเก็บกวาดของ PHP จึงลบไฟล์ session ทิ้งก่อนที่ guard ของแอปจะได้ทำงาน ผู้ใช้หลุดจากระบบตั้งแต่พักไป ~24 นาที ทั้งที่ตั้งไว้ 4 ชม. (พิสูจน์แล้ว) · ตอนนี้ `bootstrap.php` ตั้งเป็น `max(idle, absolute) + 3600`
- **ค่าคงที่จาก env ผ่าน `config_positive_int()`** — รับเฉพาะจำนวนเต็มบวก ค่าที่ตั้งผิด (`-1`, `4h`, `0`) กลับไปใช้ค่าปริยายพร้อมเขียน log ⚠️ `RATE_LIMIT_MAX_ATTEMPTS`/`RATE_LIMIT_WINDOW_SECONDS` เดิม **ไม่เคยอ่านจาก env เลย** ทั้งที่ `.env.example` เขียนไว้ให้ปรับ
- ⚠️⚠️ **กฎลำดับล็อกนี้ใช้กับ `email_change_requests` ด้วย** — `ProfileService::confirmEmailChange()` เคยจองแถวคำขอก่อนแถวผู้ใช้ ขณะที่ `changeEmail()` จองแถวผู้ใช้ก่อน · วัดจริงแล้วได้ deadlock 1213 และผู้ใช้เห็นข้อความชี้ผิดสาเหตุว่า "ลิงก์อาจหมดอายุหรือถูกใช้ไปแล้ว" ทั้งที่ลิงก์ยังดีอยู่
  · ⚠️ **เขียนกฎลงเอกสารแล้วต้องไล่ตรวจว่ามีที่อื่นละเมิดอยู่ไหม** — คอมมิตที่เพิ่มกฎนี้ แก้เฉพาะ `resetPassword` ส่วนโค้ดที่เขียนก่อนหน้านั้นแค่ก้าวเดียวยังผิดอยู่

- ⚠️⚠️ **ลำดับการจองแถวของ `users` กับ `password_reset_tokens` ต้องเหมือนกันทุกทาง — `users` ก่อนเสมอ**
